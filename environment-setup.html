The Three Tools

StringFlow Environment Setup

Installs and manages the local translation server(s) that StringFlow Translate uses. Everything it does runs through Docker, on your own machine — it never sends your project anywhere, and it never installs or starts Docker itself.

Open it from Tools ▸ StringFlow ▸ StringFlow Environment Setup.

Running the setup wizard

Press Start Setup. It walks a fixed sequence, one stage at a time:

  1. Docker. Checks that Docker Desktop is installed and running. If it isn't, you get a numbered set of steps for your platform and an I've done that — Check Again button — the wizard waits here rather than failing outright.
  2. Each engine, one at a time. For each engine you're setting up, the wizard describes what installing it involves (roughly how much it downloads, what it covers) and asks Set Up <name> or Skip This One — it never downloads anything without that explicit choice.
  3. Waiting out the first-run download. A container can be "up" in Docker's sense while it's still fetching its language models — that first download takes real time (LibreTranslate: ~20–30 minutes for its full ~50-language set). The row shows live status and the container's own latest log line the whole time.

⚠ Let the first download finish

Quitting Unity, sleeping the machine, or stopping the container mid-download can leave a half-written model file behind — which stops the server from starting at all, permanently, since the downloaded files live in a Docker volume that outlives the container. If that happens, Repair fixes it without losing what did finish downloading.

Reading a backend's status

DotStatusWhat it means
✓ReadyRunning and answering. StringFlow Translate can use it.
⚠Not answering yetContainer is up but hasn't responded — its log was checked and shows no sign of a crash, so it's genuinely still starting (usually still downloading models). The row shows the latest log line as live progress.
⚠StoppedInstalled, but the container isn't running. Press Start.
⟳Checking…Looking at Docker and the server right now — a few seconds, not a state you'll see for long.
✗Not set upNothing installed yet. Press Set Up.
✗ErrorSomething is genuinely wrong and the row names it — this is never a "just wait" state. See Troubleshooting.
⚠Port conflictSomething else on your machine already holds the port this backend wants. The row names the process. See Troubleshooting.

The backend row's actions

Each backend gets one card with one primary button — whatever's actually relevant right now — plus a ⋯ menu for the rest: Check Again, Start / Stop / Restart, Repair, Open in Browser, and Enable / Disable for Translator.

If a backend is already answering under the URL you've configured — however it was started, by this tool or by hand — it's treated as Ready immediately. StringFlow never reinstalls over the top of something that's already working, and if it finds a container it didn't create sitting on the right port, it adopts and manages that one instead of creating a duplicate.

CPU vs. GPU

A backend that offers a GPU-accelerated build (NLLB does) shows a CPU / GPU dropdown next to its card. CPU is the safe, portable default — it works on any machine Docker runs on, Apple Silicon and ARM included. GPU needs an NVIDIA GPU and Docker's GPU passthrough working (on Windows, that means Docker Desktop's WSL2 GPU support) — pick it only if you know that's set up, since a GPU build on a machine without working passthrough will fail to start rather than silently fall back to CPU.

Repair

When a server is crash-looping in a way that looks like a half-finished model download, the row's error explains that plainly and offers a Repair button — in place of the normal primary action, and also in the ⋯ menu. Repair:

  1. Stops the container.
  2. Deletes only what's provably incomplete. It scans the server's model-data folder in a disposable helper container and removes any model directory containing a zero-byte file — the exact signature of a download that was cut off. Every model that finished downloading completely is left untouched.
  3. Starts the container again, which re-downloads only what was removed.

Nothing about Repair is guesswork: it only ever removes files that are unusable by definition, never anything that could still be good.

Enabling NLLB

NLLB is StringFlow's optional second engine — broader language coverage, at the cost of a much heavier setup. It's disabled by default and gated behind a licence notice: its model is released under a non-commercial licence, and the tool won't let you install it until you've read that notice and ticked the box confirming you understand it. See Licensing — NLLB before enabling it on a commercial project.

The dashboard, once everything's set up

This same window doubles as the day-two view once setup has run at least once — the step-by-step wizard hands off to a compact dashboard rather than showing you a finished checklist every time you open it:

  • A one-line Docker status at the top — a green check, or a red cross with its own Fix This button that re-runs the same wizard flow from the top if Docker stops being available.
  • One card per backend — exactly the same cards and actions described above.
  • Restore the engines that ship with this package — appears only if your backend list is missing one of StringFlow's own default engines (deleted from StringFlow Routing, say). Puts back whatever's missing, exactly as shipped, without touching anything still in your list — so a custom backend you added yourself is never affected.
  • Run Setup Again — re-enters the same wizard flow. Safe to press any time; see Coming back later below for why.

The Diagnostic Log

A collapsible, timestamped log at the bottom of the window — every check, install, start, stop, and repair step this tool has ever run appends a line here, tagged with which backend it was about, so a failure can be traced back through everything that actually happened rather than just the last status line you can see. Copy puts the whole thing on your clipboard (useful for reporting an issue); Clear empties it. This is the first place to look when a wizard step or a backend fails for a reason its own status text doesn't fully explain.

Coming back later

Start Setup (or Run Setup Again from the dashboard) is safe to run any time — it's idempotent. Anything already Ready is skipped straight through with no prompt, anything merely Stopped is started with no prompt, and nothing already downloaded or built is ever fetched a second time. It's also what a returning user needs after a restart: containers with a restart policy come back on their own once Docker Desktop is running, so most of the time this just confirms everything's already fine.
