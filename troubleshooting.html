Something looks stale or out of date

This is the single most common source of confusion across all three tools, and it's almost always the same underlying cause: a window is showing you a cached snapshot, taken the last time it actually read the project — not a live view that updates the moment something changes elsewhere. It isn't a bug in Unity's repaint system; it's a deliberate performance choice (re-reading everything on every frame would make a large project sluggish), and each tool gives you an explicit way to force a fresh read:

WhereWhat's cachedHow to force a fresh read
StringFlow Tables (main window) Its own Scan button deliberately reuses cached results for anything unchanged. Press Refresh instead of Scan — see Scan vs. Refresh.
Coverage, Find Duplicate Text, Find Unused Keys All three read the main window's last scan results — they never scan on their own. Run Refresh in the main window first, then reopen (or use each window's own Refresh where offered).
StringFlow Translate's table/locale/key list Read once when the window opens, and cached from there. Press its Refresh button — or close and reopen the window, which forces the same re-read.
StringFlow Languages LibreTranslate's language list specifically is only as current as its last live Test this session. Test the backend in StringFlow Translate — see below.

As a general rule: if you changed a table, translated something, or cleared values in one window while another was already open showing the same data, the second window won't notice on its own. Refresh it, or close and reopen it, before trusting what it shows.

Port conflict

The backend's row names exactly what's holding the port — read that first. The single most common cause, by platform:

PlatformUsual causeFix
macOS ControlCenter — this is AirPlay Receiver, which has claimed port 5000 since Monterey. Turn off System Settings ▸ General ▸ AirDrop & Handoff ▸ AirPlay Receiver, or change the port instead (next column).
Any Another dev server, or a leftover container from a previous session. Close it, or in StringFlow Routing change the backend's URL to a free port, e.g. http://localhost:5001, then press Check Again in StringFlow Environment Setup.

If you change the port, only the number before the colon in the URL changes — the server still listens on the same port inside its container, StringFlow's default publish mapping just changes which host port reaches it. Setting the URL is enough; nothing else needs updating.

"Starts, crashes, and restarts over and over"

This means Docker reports the container as running, but it's actually failing on every boot — waiting longer will never fix it, and StringFlow says so instead of leaving you to wait out its normal 45-minute timeout for nothing.

  • If a Repair button is offered, the log pointed at a half-finished model download — almost always caused by interrupting the very first setup (closing Unity, sleeping the machine, or stopping the container while it was still downloading). Press Repair; it removes only the files that never finished and re-downloads just those. See Environment Setup — Repair.
  • If not, open the Diagnostic Log at the bottom of StringFlow Environment Setup for the container's actual error. Common causes: ran out of disk space mid-setup, or a GPU variant selected on a machine without a working GPU passthrough (try the CPU variant instead). If nothing there explains it, the surest fix is removing the container and running Set Up again from scratch (stop it first from the ⋯ menu).

Repair on NLLB just restarts it, without cleaning anything up

This is expected, not a bug. Repair's surgical clean-up (removing only the model files that never finished downloading) needs to know exactly where a backend keeps its downloaded model data — LibreTranslate declares this, so Repair can be precise for it. NLLB doesn't declare a model-data path the same way, so Repair has nothing safe to selectively delete and falls back to a plain restart instead, rather than guessing at a path and risking a good model. If an NLLB container is genuinely stuck, the fix is the same as any other crash-loop without a Repair option: check the Diagnostic Log, and if nothing there explains it, remove the container and run Set Up again from scratch.

GPU selected, but it doesn't seem to be using it

A GPU-variant container that starts successfully but still translates slowly, or a container that fails to start at all right after switching to GPU, both point at the same thing: Docker's GPU passthrough isn't actually working on this machine. On Windows this specifically needs Docker Desktop's WSL2 GPU support enabled with a supported NVIDIA driver; on Linux it needs the NVIDIA Container Toolkit installed. Switching back to CPU always works regardless of any of this — it's the portable default for exactly this reason.

Docker isn't ready, even though it's running

Unity reads your system PATH once, when it launches. Docker installed after that — or added to PATH by its own installer mid-session — can be genuinely invisible to an Editor that's already open.

  1. Restart Unity. This alone fixes it most of the time.
  2. Still not found? In StringFlow Environment Setup's Docker section, use Locate docker myself… and point directly at the docker program (docker.exe on Windows). It's tested with --version before being saved, so a wrong file is caught immediately rather than failing later.

A download or pull fails or hangs

If Docker itself is confirmed running (green in StringFlow Environment Setup) but pulling or building a specific backend fails or never progresses, the cause is almost always something sitting between Docker and the internet, not StringFlow itself:

  • Corporate firewall or proxy — Docker Hub and Hugging Face both need outbound HTTPS access; a network that blocks or intercepts that will show up here as a pull that hangs or fails with a TLS/certificate error.
  • Antivirus scanning every layer — some antivirus products scan Docker's image layers as they're written, which can make a pull look stalled when it's actually just very slow. Give it time before assuming it's stuck.
  • Disk space — a pull that fails partway through with no clear network error is worth checking against free disk space before anything else.

Stuck on "not answering yet"

Check the log line shown right under the status — it updates live. If it's genuinely moving (different text a few seconds later), it's still downloading or loading; this is normal on a first run and can take 20–30 minutes. If the line hasn't changed in several minutes and looks like an error rather than progress, open the Diagnostic Log for the full picture, or try Check Again to force an immediate re-read of the container's log.

Only StringFlow Tables shows up under Tools ▸ StringFlow

Unity's own Localization package isn't installed. StringFlow Translate and StringFlow Environment Setup both require it and simply don't compile without it — which is deliberate: rather than a wall of compile errors in your console, those two menu items just don't appear, and you'll see one warning in the console the first time you open the project explaining why. Install it via Window ▸ Package Manager ▸ Unity Registry ▸ search "Localization" ▸ Install; the menus appear on their own once Unity finishes recompiling. StringFlow Tables doesn't need this package and works either way.

A language isn't in the list

Open StringFlow Languages (from the button in StringFlow Translate) to see exactly what the currently running server(s) support. A locale missing from that list is skipped for that backend rather than causing a failure — if you have more than one backend enabled, StringFlow tries the next one automatically. Adding a new Locale to your Unity project later needs no re-setup on the server side; if the server already covers that language, it just works the next time you translate.

StringFlow Languages shows 0 languages for LibreTranslate

This doesn't mean the server has no languages — it means LibreTranslate hasn't been tested this Editor session yet. Unlike every other backend (whose languages come from a static map), LibreTranslate's list is discovered live, and StringFlow Languages only ever reads whatever the last live test found; it never makes a network call of its own. Go to StringFlow Translate and press Test All (or test that one backend directly), then reopen StringFlow Languages.

Translate ran, but nothing changed

Every target cell in scope was already filled — StringFlow Translate only ever writes to empty cells, by design (see StringFlow Translate). A dialog says so explicitly ("Nothing to translate — all applicable cells are already filled") rather than silently doing nothing, so if you saw that message, this is confirmed, not a guess. Switch to Selected Missing with specific keys checked to confirm exactly what's outstanding, or use StringFlow Tables' Coverage view to see the gaps directly. And if you expected a cell to be re-translated rather than filled for the first time, remember it needs to be genuinely empty first — see Clear Values.

"Source and target are the same locale"

Shown when Source Language and Target Language resolve to the same locale for the current selection — there's nothing to translate by definition. This most often happens with Auto source resolution on a table where a key's only non-empty value happens to be in the same locale you've picked as the target. Pick an explicit, different source locale, or check which locale actually has content for the affected keys.

A run stopped partway through on its own

Closing StringFlow Translate's window mid-run is treated as an implicit cancel — whatever already completed is kept, exactly like pressing Cancel yourself. The most common way this happens by surprise is a script recompile: editing and saving a C# script while a long translation run is in progress reloads the Editor's scripting domain, which closes the window's live state along with it. If you're about to kick off a large run, avoid triggering a recompile until it's done — or just re-run it afterward, since StringFlow Translate only fills empty cells, picking back up exactly where it left off costs nothing.

Bind / Change Table button isn't there for a row

These are status-specific by design: Bind only appears for Unlocalized rows, and Change Table only for rows that are already bound to something (any status other than Unlocalized). If neither shows up, check the row's actual status first — a Missing Key or Broken Binding row gets a Repair section instead, since "bind" and "fix an existing broken binding" are different operations with different safe defaults.

Unused Keys (or Coverage) looks wrong

Both windows read the main window's most recent scan, not a fresh scan of their own — see Something looks stale or out of date above. If that scan was a narrow scope like Current Scene, a key used only elsewhere in the project will show as unused (or coverage will look worse than it really is) even though it's genuinely fine. Run a scan with Entire Project in the main window first, then reopen whichever of these you were looking at.

Ctrl+Z didn't undo something

Almost everything in StringFlow Tables is undoable — Bind, Unbind, Change Table, Merge Keys, Delete Unused Keys, Clear Values all go through Unity's normal Undo system. The one deliberate exception: any write that lands on a prefab asset directly (not a scene instance of one) — most commonly "Match Prefab Binding" on a prefab override, or a Bind/Change Table/Repair batch that happens to include prefab-asset objects. The Preview window always warns you before you apply anything that includes one of these, specifically because it's the one case Ctrl+Z can't undo — if you saw that warning and clicked Apply anyway, that's why.

A history entry says "(deleted)"

This is StringFlow History being honest about a key or table that no longer exists, rather than silently dropping the record or crashing. History identifies entries by stable internal IDs, not by name, so renaming a table, key, or locale never breaks anything here — only actual deletion does, and even then the historical record of what was translated, when, and by which backend is kept; it just can't be pinged open in the Table window any more.

Entire Project scan is slow, or the Editor feels unresponsive

Scanning every scene and prefab in a large project is genuinely more work than scanning one scene, and it's the slowest option on purpose — it trades speed for completeness. The results list itself stays responsive regardless of size (only visible rows are actually drawn), so if the Editor seems to hang, it's most likely mid-scan rather than stuck; a progress bar with its own Cancel is shown for exactly this. For routine iteration, prefer Current Scene or Selected Prefabs and save Entire Project for before a translation pass or a release.

A translation reads oddly

Check its tag in the table. Translated via segment fallback (shown as Filled, needs review in StringFlow Translate's key list) means the string had to be split and reassembled — usually because of placeholders or Rich Text tags in the middle of the sentence — and is the kind of result worth a native speaker's review before it ships. Machine translation in general is a first pass, not a final one; treat anything player-facing as a draft until a human has looked at it.
