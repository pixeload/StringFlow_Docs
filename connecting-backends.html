Connecting Custom Backends

StringFlow Translate doesn't hardcode LibreTranslate or NLLB into how it talks over the network — both speak the same small REST contract, and any server that speaks it plugs in exactly the same way, with no code changes. This page is that contract, and how to wire a new backend into StringFlow once you have one.

The REST contract

This is the entire interface. Implement these two endpoints and StringFlow can use your server exactly as it uses LibreTranslate or NLLB — as a fallback candidate, a rule target, or the only backend you have.

POST /translate

Request (single string)

{
  "q": "Hello, world",
  "source": "en",
  "target": "hi",
  "format": "text"
}

Response

{ "translatedText": "नमस्ते, दुनिया" }

Batched form — StringFlow sends this automatically whenever it has 2+ strings to translate in the same request, to cut down on round-trips. Your server can ignore this entirely and only support the single-string shape above; StringFlow detects that from the response shape and falls back to one request per string for the rest of the run.

Batched request

{
  "q": ["Hello", "Goodbye", "Thank you"],
  "source": "en",
  "target": "hi",
  "format": "text"
}

Batched response — same order as the request's "q"

{ "translatedText": ["नमस्ते", "अलविदा", "धन्यवाद"] }

Error response (any non-2xx status)

{ "error": "a human-readable message" }

GET /languages

Advertises what your server can translate, and — critically for LibreTranslate-style backends — is what StringFlow uses to discover languages live rather than from a hardcoded list, so a server that adds a language later needs no update on the Unity side at all. 

[
  {
    "code": "en",
    "name": "English",
    "targets": ["hi", "ja", "fr", "es"]
  },
  {
    "code": "hi",
    "name": "Hindi",
    "targets": ["en"]
  }
]

targets matters: StringFlow checks it per source language rather than assuming every language in the list can translate into every other one, since real MT servers rarely have every directional pair.

Adding a backend in the UI

  1. Open Tools ▸ StringFlow ▸ StringFlow Translate and press Configure Routing… to open StringFlow Routing.
  2. Under Backends, press Add Backend. You get a new entry named New Backend, disabled, pointed at http://localhost:5003 — a placeholder, not a real default.
  3. Set its real URL, then press Test. A green result means GET /languages answered successfully.
  4. Tick it on to enable it. Nothing else is required for a backend that speaks LibreTranslate's exact language codes (bare ISO codes like en, hi, ja) — StringFlow discovers what it supports from GET /languages automatically, the same way it does for LibreTranslate itself.

Language code maps

Only needed if your server's language codes aren't discoverable this way, or use a different scheme than Unity's own Locale codes — the way NLLB uses FLORES-200 codes like tel_Telu for Telugu instead of Unity's te.

In StringFlow Routing, scroll to your backend's language map section and add entries: a Unity locale code on one side (te), your server's own code for that language on the other (tel_Telu). A locale with no entry simply isn't attempted on that backend — never a hard failure, since the router tries the next candidate in the fallback chain instead. So this map never needs to be exhaustive; add languages to it as you actually need them.

Routing: rules, priority, and learning

StringFlow decides which backend handles a given (source, target) pair in this order:

  1. Rules. An ordered list of source → target → backend — either side can be * to match anything. Evaluated top to bottom; the first enabled match wins that pair's preferred backend. Add one with Add Rule in StringFlow Routing.
  2. Dynamic Routing (if enabled). The backend that most recently actually succeeded for that exact pair, remembered automatically — gets faster the more you translate, and never needs configuring by hand.
  3. The fallback order — the reorderable priority list shown in both StringFlow Translate and StringFlow Routing (drag, or use ▲ / ▼).

At every level, this is a preference, not an exclusive assignment. If the preferred backend can't actually serve a pair — disabled, no language code, or a genuine failure at translate time — StringFlow keeps walking the rest of the fallback order rather than treating that as the job's final answer. A job only actually fails once every candidate has been tried.

Optional: teaching Environment Setup to manage it

A backend added through Add Backend is what StringFlow calls manually managed: StringFlow Environment Setup will health-check its URL (so it still shows up as Ready/Not answering there), but it will never install, start, stop, or otherwise touch it — that server is entirely yours to run.

Making Environment Setup able to install and run your backend too — the way it does for LibreTranslate and NLLB — means your server needs to run in Docker and be editable as project data, which isn't exposed through the UI; it's a small code-level addition (a DockerImagePull or DockerBuildBundled backend definition). If you need this, it's a reasonable ask for support — the underlying design already treats every backend generically, so this was built to be extended.

Minimal reference server

A working, dependency-light example — enough to test the contract against, or use as a starting point. Python, no framework beyond the standard library: 

from http.server import BaseHTTPRequestHandler, HTTPServer
import json

LANGUAGES = [
    {"code": "en", "name": "English", "targets": ["hi"]},
    {"code": "hi", "name": "Hindi", "targets": ["en"]},
]

class Handler(BaseHTTPRequestHandler):
    def _send_json(self, obj, status=200):
        body = json.dumps(obj).encode("utf-8")
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def do_GET(self):
        if self.path == "/languages":
            self._send_json(LANGUAGES)
        else:
            self._send_json({"error": "not found"}, 404)

    def do_POST(self):
        if self.path != "/translate":
            self._send_json({"error": "not found"}, 404)
            return
        length = int(self.headers.get("Content-Length", 0))
        req = json.loads(self.rfile.read(length))

        # Replace this with a real translator. This stub just tags the input
        # so you can see the round-trip is working end to end.
        def fake_translate(text):
            return f"[{req['target']}] {text}"

        if isinstance(req["q"], list):
            self._send_json({"translatedText": [fake_translate(s) for s in req["q"]]})
        else:
            self._send_json({"translatedText": fake_translate(req["q"])})

if __name__ == "__main__":
    HTTPServer(("0.0.0.0", 5003), Handler).serve_forever()

Run it, add it in StringFlow Routing pointed at http://localhost:5003, press Test — a green result means the contract is satisfied and StringFlow can already route work to it.
